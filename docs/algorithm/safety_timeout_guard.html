안전 계층

safety_timeout_guard

이 node는 planner와 flight controller 사이의 hard gate입니다. 더 나은 path를 계산하지는 않고, 현재 planner command가 충분히 fresh하고 safe한지 여부만 판단합니다.

중요한 입력이 stale하면 이 node는 zero velocity를 publish하고 safety reason code를 남깁니다.

입력과 출력

  • 입력: pose, raw scan, planner command
  • 출력: safe command, safety event string
  • 주 command path: /drone1/autonomy/cmd_vel -> /drone1/safety/cmd_vel

핵심 아이디어

stale data를 unsafe data로 취급합니다. 시스템이 pose, scan, planner command freshness를 잃으면, pipeline이 다시 건강해질 때까지 motion 전달을 멈추는 것이 가장 안전하다는 철학입니다.

판단 순서

  1. startup grace time 동안 모든 motion을 hold합니다.
  2. pose가 없거나 pose_timeout_sec보다 오래됐으면 command를 차단합니다.
  3. require_scan이 켜져 있으면 scan timeout 시 command를 차단합니다.
  4. planner command가 없거나 stale하면 차단합니다.
  5. 필요하면 nearest scan distance가 threshold 아래일 때 emergency stop을 겁니다.
  6. 모든 검사가 통과했을 때만 latest planner command를 safe command로 전달합니다.

보게 되는 Safety Reason

  • startup_grace
  • pose_timeout
  • scan_timeout
  • planner_cmd_timeout
  • emergency_stop_obstacle
  • normal

로그에서 어떻게 보이는가

  • 시작 로그: Safety monitor ready: ...
  • 상태 전환: Safety state changed: <reason>
  • 중간에 motion suppression이 반복되면 mission은 성공해도 과정이 불안정해 보일 수 있습니다.

왜 report에서 중요한가

어떤 run은 HOVER_AT_GOAL로 끝나도, safety layer가 timeout이나 emergency-stop 상태를 반복하면 중간 구간은 꽤 요동칠 수 있습니다. 그래서 최신 report는 final outcome만이 아니라 stability counter, root-cause summary, streak analysis까지 함께 보여주도록 바뀌었습니다.
