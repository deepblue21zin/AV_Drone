AV_Drone 현재 상태 종합 가이드

현재 저장소는 단일 드론 기준으로는 꽤 잘 정리된 연구형 baseline이며, 실제 active runtime은 LiDAR 기반 follow-the-gap 회피 비행입니다. 다만 최종 목표는 여기에 SLAM 기반 맵 생성, 복귀 MPPI, 그리고 3드론 동적 시뮬레이션까지 확장하는 것입니다.

현재 구조는 패키지 분리가 잘 되어 있어 팀 분리 개발에 유리합니다. 핵심은 알고리즘 본체와 운영 런치/로그가 서로 다른 패키지에 있다는 점입니다.

현재 강점

  • 패키지 경계가 비교적 명확합니다.
  • 실험용 MPPI 계열과 active planner가 분리되어 있습니다.
  • 운영 로그와 audit 체계가 같이 있습니다.

현재 약점

  • selector / behavior manager는 아직 없습니다.
  • SLAM은 scaffold 수준입니다.
  • MPPI는 아직 planner-only 구조가 아니라 독립 미션형입니다.

중요한 원칙

  • 지금은 한 번에 하나의 개발 프로필만 실행합니다.
  • 공통 baseline 코드는 통합 전까지 안정적으로 유지합니다.
  • 토픽 계약을 먼저 고정하고 알고리즘을 각자 고도화합니다.

3. 각각 어디 코드를 수정하면서 개발해야 하는지

현재 개발 방식은 알고리즘별 패키지 분리 + launch/profile 분리가 기본입니다. 각 담당자는 자기 패키지 안 알고리즘만 수정하고, 공통 baseline 축은 통합 전까지 최대한 건드리지 않는 것이 좋습니다.

회피 담당

수정 중심: src/drone_planning/drone_planning/local_planner_node.py

  • gap 탐색, bubble, score, escape 로직
  • 개발 프로필 설정: src/drone_bringup/config/drone1_avoidance_dev.yaml
  • 실행: ros2 launch drone_bringup single_drone_avoidance_dev.launch.py

SLAM 담당

수정 중심: src/drone_slam/

  • 현재 scaffold를 실제 SLAM node로 교체
  • map_ready, localization_ok, home_pose 등 인터페이스 유지
  • 실행: ros2 launch drone_bringup single_drone_slam_dev.launch.py

MPPI 담당

수정 중심: src/mppi/mppi/mppi_node.py

  • rollout, cost, obstacle handling, return trajectory
  • 현재는 독립 미션형 노드라 planner core 분리 필요
  • 실행: ros2 launch drone_bringup single_drone_mppi_dev.launch.py

MPPI_LiDAR 담당

수정 중심: src/mppi_lidar/mppi_lidar/mppi_lidar_node.py

  • scan clustering, dynamic obstacle 추정, LiDAR 직접 비용화
  • launch/config는 src/mppi_lidar/launch, src/mppi_lidar/config
  • 실행: ros2 launch mppi_lidar mppi_lidar.launch.py
공통축 코드현재 역할통합 전 권장사항

4. 최종 원하는 목표와 논문 발전 방향

최종 시스템 목표

출발: reactive avoidance + LiDAR SLAM
-> 목표 지점 도착
-> map 품질 / localization 품질 확인
-> 복귀: MPPI 또는 MPPI_LiDAR 기반 최적경로
-> 최종: 3드론 동적 시뮬레이션 + 역할 분담 + 안전 복귀
  • 출발 구간은 현재 회피 플래너가 담당합니다.
  • 동시에 SLAM이 맵과 home pose를 쌓습니다.
  • 복귀 구간은 map_ready, localization_ok를 만족할 때 MPPI가 담당합니다.
  • 복귀 중 MPPI 실패 시 reactive fallback이 필요합니다.
  • 최종 3대 체계에서는 각 드론 로컬 스택 위에 fleet manager가 올라갑니다.

논문으로 발전시키는 길

Reactive OutboundMap-based ReturnSwitching PolicyDynamic World
  • 주제 1: 출발은 reactive, 복귀는 map-based optimal control이라는 이중 planner 구조
  • 주제 2: map 품질과 localization 신뢰도에 따라 planner를 바꾸는 switching policy
  • 주제 3: 3드론 환경에서 협업 탐색 후 안전 복귀까지 포함한 mission-level 연구
  • 주제 4: dynamic obstacle / moving target 환경에서 return policy의 강건성 비교

논문 KPI 후보

  • success rate
  • time to goal / return
  • minimum clearance
  • path length
  • switch count
  • recovery latency

비교 실험군

  • reactive only
  • MPPI only
  • reactive + map return
  • reactive + MPPI_LiDAR return

논문 품질 포인트

  • 동적 시나리오 재현성
  • 실패 케이스 분석
  • 다회 실행 통계
  • run-to-run 비교 자동화

  • 운영 로그와 보고서 품질이 좋습니다.
  • 팀 분리 개발 구조로 바꾸기 좋습니다.
보강 포인트
  • SLAM과 MPPI를 공통 계약으로 묶는 계층이 없습니다.
  • run 비교 자동화가 아직 약합니다.
  • planner switch와 fallback 지표가 아직 부족합니다.
현업에서 막히는 지점
  • 동적 시나리오 검증 부재
  • 3드론 orchestration 부재
  • 실패 복구 / task reallocation 부재

10. 최종 목표를 동적 시뮬레이션으로 정리

최종 목표는 단순히 “드론이 한 번 목표점에 갔다 오는 것”이 아닙니다. 동적 장애물과 다중 드론이 존재하는 환경에서, 나갈 때는 reactive + SLAM으로 버티고, 돌아올 때는 map-aware MPPI로 더 똑똑하게 복귀하는 구조를 시뮬레이션으로 증명하는 것이 핵심입니다.

Stage A. 현재 상태
단일 드론 + 정적 장애물 + reactive avoidance + metrics/report

Stage B. 다음 단계
단일 드론 + LiDAR SLAM + home/map 저장 + return MPPI 단독 검증

Stage C. 통합 단계
단일 드론 + dynamic obstacle + planner selector + fallback policy

Stage D. 최종 목표
3드론 + dynamic simulation + fleet manager + shared mission report

동적 시뮬레이션에서 반드시 보여야 하는 것

  • 움직이는 장애물 또는 시간에 따라 바뀌는 통로
  • outbound에서 reactive planner가 충돌 없이 목표 지점 도달
  • 동시에 SLAM이 map과 home pose를 안정적으로 축적
  • return 시점에 planner selector가 MPPI로 전환
  • map 품질이 나쁘면 reactive fallback 또는 safe hover 수행
  • 3드론 최종형에서는 서로의 간격과 역할을 fleet manager가 관리

성공 기준 예시

  • 단일 드론: 20회 중 18회 이상 목표 도달 및 안전 복귀
  • 동적 장애물: 충돌 0회, unsafe streak 지정 임계치 이하
  • MPPI 복귀: reactive 복귀 대비 평균 경로 길이/복귀 시간 개선
  • 3드론: 전체 임무 완료율 85% 이상, inter-drone minimum distance 유지
  • 보고서: active planner, switch reason, root cause, previous run 비교 포함
최종 해석: 이 프로젝트의 완성형은 “회피 알고리즘 하나”가 아닙니다. 탐색 단계와 복귀 단계를 분리하고, 동적 환경과 멀티드론까지 설명 가능한 운영형 autonomy stack으로 발전시키는 것입니다. 그 지점까지 가야 연구 서사도 생기고, 현업 관점에서도 설득력이 높아집니다.
